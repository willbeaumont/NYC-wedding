# Wedding-week forecast and persisted dark mode

The change adds a discoverable three-day New York weather widget that fetches Open-Meteo only when the complete October 7–9 range enters its 16-day horizon, while retaining static copy and a National Weather Service link for every fallback state. It also adds an early system-aware theme selection, a persisted manual toggle, dark/responsive/print styling, and controlled Node tests around forecast and preference behavior. The forecast path is resilient and keeps itinerary content independent of the third-party request, but the dark palette introduces foreground collisions on the most prominent surface. Watch for: **[confirmed]** unreadable dark-mode hero/header text, **[confirmed]** sub-AA dark-mode tip labels, **[confirmed]** an inert theme button when JavaScript is unavailable, and **[confirmed]** tests that do not exercise those integrated states.

**Verdict**: NEEDS_CHANGES

## Remediation iteration 1

**Status**: RESOLVED

All four confirmed issues were fixed:

1. Hero and header text now use an invariant `--hero-foreground` token instead of the theme surface token. Regression tests verify the foreground against both fixed gradient endpoints.
2. Small "Good to know" labels now use `--accent-text`, with a dark value that meets WCAG AA against the notes surface. The concrete dark pairing is covered by a contrast test.
3. The theme toggle is hidden by default and becomes visible only after JavaScript attaches its click behavior and adds the `theme-ready` class.

## High-level view

The forecast is a progressive enhancement over three static event-date cards. Availability is calculated in New York calendar dates, requests are suppressed until all three dates fit the provider horizon, and early, underway, past, malformed, offline, HTTP, and timeout outcomes retain honest fallback messaging and a direct forecast link.

The theme implementation resolves a validated stored preference before CSS loads, otherwise follows the operating system, and stops following system changes after a manual choice. **[confirmed]** The new dark token values are also inherited by hero and header foreground declarations that were written against light-theme token semantics, reducing title and navigation contrast to roughly 1.11–1.39:1 on the unchanged dark gradient; the dark palette therefore is not shippable as implemented.

The dark-mode work covers most cards and muted copy, but **[confirmed]** the numbered labels in the “Good to know” section remain `#a87837` against the new `#182f28` surface, producing only 3.66:1 contrast at 0.68rem. **[confirmed]** The manual toggle is emitted as a normal visible button even when scripts are disabled, unlike the existing copy controls, so no-script visitors receive a control that cannot change the theme.

The controlled tests cover forecast success/failure and theme state, but **[confirmed]** they do not check the hero/header and small-label color pairings or the no-script control state.

## Forecast horizon, fallback, and provider trust boundary

The widget uses fixed NYC coordinates, `America/New_York`, Fahrenheit, and only the four daily fields needed by the cards. It waits until October 9 is no more than 15 days after the current New York date, which makes the inclusive range fit the documented 16-day horizon, and deliberately stops presenting API data once the event week is underway. Static card text and the National Weather Service link remain available without a successful request, while returned arrays are checked for matching lengths, required dates, and finite values before any card is updated.

The browser contacts a fixed HTTPS Open-Meteo endpoint without credentials, location permission, user input, cookies, or executable third-party assets. Open-Meteo sees normal request metadata such as the visitor IP during the forecast window, and the README discloses that boundary. Provider output is rendered through `textContent` after structural validation, so the new network path does not create an HTML-injection surface.

## Dark palette leaks surface tokens into hero foregrounds

**[confirmed]** `styles.css` redefines `--paper-light` from light parchment (`#fbf8f1`) to a dark surface (`#182f28`), but `.site-header` and `.hero` continue to use `color: var(--paper-light)`. Their background remains the fixed `#21483d` to `#102720` hero gradient, leaving the wordmark, navigation links, heading, and inherited ghost-button text at only about 1.39:1 to 1.11:1 contrast. The hero should use a dedicated invariant-on-dark foreground token or an explicit light value, and dark-mode coverage should assert the actual hero/header foreground against the gradient rather than only checking root variables.

**[confirmed]** The numbered `.tips-grid article > span` labels retain the light-theme brown `#a87837` while `.notes` changes to the dark `--paper-light` surface. The resulting 3.66:1 contrast misses the 4.5:1 threshold for this 0.68rem text. A dark-theme override or semantic accent-text token is needed, with that concrete pairing added to the contrast checks.

**[confirmed]** `#theme-toggle` is always visible in the static markup, but its click behavior exists only in deferred JavaScript. If JavaScript is disabled or fails before initialization, system dark styling still works but the button advertises a manual switch that does nothing; this is inconsistent with the existing copy buttons, which are hidden until `.js` is present. Hide the toggle by default and reveal it after enhancement initializes, or provide a non-script interaction model.

## Controlled logic coverage misses rendered theme combinations

The forecast tests execute a successful payload and an offline rejection with controlled doubles, and the theme tests cover persisted dark mode, system changes, explicit selection, and blocked storage. **[confirmed] Not tested:** the available-window boundary, malformed/HTTP/abort outcomes, the dark hero/header’s effective foreground against its fixed background, the “Good to know” label contrast, and the no-script state of the theme control. The first group is directly traceable in the implementation, but the three dark-mode omissions allowed user-visible accessibility regressions through despite the palette test; add integration-level style contracts for those surfaces and a no-script control assertion before relying on the dark-mode coverage.
