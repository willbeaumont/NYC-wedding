# Wedding-week forecast and persistent dark mode

The change adds a discoverable New York forecast for October 7–9, gated to Open-Meteo’s 16-day horizon and backed by static fallback copy plus a direct National Weather Service link. It also adds early system-aware theme selection, a persisted light/dark control, responsive dark surfaces, print treatment, and controlled tests for both feature paths. The four findings from the first review are resolved, and the build plus all 19 tests pass on this pass, but the toggle now combines a changing action label with toggle-state semantics that communicate contradictory state to assistive technology. Watch for: **[confirmed]** after selecting dark mode, the control is exposed as “Use light mode” while also marked pressed, so its accessible name no longer identifies the option whose pressed state is being reported.

## Forecast horizon and provider trust boundary

The fixed NYC request sends no credentials, location permission, or user-entered coordinates, and the README discloses that Open-Meteo receives normal request metadata during the forecast window. The complete October 7–9 range must fit before the browser makes a request, and the response arrays must contain every event date with finite condition, temperature, and precipitation values before any cards are populated. Rendering uses `textContent`, while every failure state retains the direct forecast link, limiting both injection exposure and the impact of provider failure.

## Theme toggle reports the next action as the pressed option

**[confirmed]** `applyTheme` sets both the visible/accessibility label to the next action and `aria-pressed` to the current dark-state boolean. After dark mode is selected, Chromium exposes a button named “Use light mode” while the DOM reports `aria-pressed="true"`; toggle-button semantics attach “pressed” to the named option, so this reads as though light mode is active even though dark mode is active. The inverse state is similarly ambiguous: “Use dark mode” is reported not pressed even though that text is intended as an action rather than a stable option label.

Use one semantic model consistently. A toggle button can keep a stable name such as “Dark mode” and let `aria-pressed` communicate whether that option is active, or an action button can keep the changing “Use light/dark mode” label and omit `aria-pressed` while exposing current state separately if needed. This should be covered by asserting the computed accessible contract after both initialization and activation, not just checking the raw state and label independently.

## Remediation coverage leaves the combined control contract untested

The first-pass concerns are addressed with an invariant hero foreground, a dark-safe tip-label token, enhancement gating for the theme control, and direct coverage of the forecast boundary and failure variants. **[confirmed] Not tested:** the relationship between the toggle’s accessible name and `aria-pressed` after state changes. The current theme test expects “Use light mode” and `aria-pressed="true"` as separate values, effectively preserving the contradiction instead of verifying that the combined announcement identifies either a stable option state or a clear action.
